# Changelog

## Unreleased

- `robot_hand`: another extension can cancel the open dialog with `robot-hand:answer` `{ version: 1, id, answerId, cancel: true }` (no digest, no choice, no other key). The dialog closes without placing or running anything, `answer-result` is `accepted: true`, and `robot-hand:closed` is `{ version: 1, id, by: "cancel", answerId }`. The tool returns a result that says the dialog was cancelled from another device or by auto mode, not by the user (`details: { status: "cancel", cancelledFrom: "remote" }`); the agent's turn is not aborted. A cancel for a dialog that already closed gets `accepted: false, reason: "closed"`; one that carries a choice, a digest, or any other key is refused as `malformed` and the dialog stays open.
- A remote cancel is told from a local Escape by its `answerId`: Escape (and "No, thanks" and "Report the mismatch and refuse") still closes with `by: "cancel"` and no `answerId`, and returns the plain declined text.
- `robot-hand:pending` carries `cancellable: true`, so an answerer knows this version takes a cancel.

## 0.7.2

- git hooks are matched to the git commands that run them, from a table of git's hooks, instead of a short list of commands: `reference-transaction` for any command that updates a ref (`branch`, `tag`, `fetch`, `reset`, `stash`, …), `post-index-change` for any command (`git add`, and `git status` when it refreshes the index), `post-checkout` for `clone`, `worktree`, and `bisect` too, `pre-auto-gc` for `gc` and `fetch`. A git command the scan does not know, and an alias whose values name none it knows, may run every hook. A `core.hooksPath` folder is listed from the top of the work tree and filtered the same way, so a husky repository's `git status` is not flagged; a folder the scan cannot list is still reported. Other files with a hook-like name are counted, never shown.
- The table follows git 2.54 as tested: a push runs the receiving repository's hooks (`pre-receive`, `post-receive`, …; a push to `.` is this repository), `restore` and `stash` run `post-checkout`, `init` runs `reference-transaction`, and `pre-merge-commit` is merge's and pull's only. Hook file names match in any case, as git runs them on a case-insensitive file system. `--no-verify` skips each command's own hooks (`pull --rebase --no-verify` still runs `pre-rebase`), and an option's value (`commit -m -n`) is not read as an option.
- A relative `core.hooksPath` is reported whole instead of listed when the work tree is set elsewhere (`core.worktree`, `GIT_WORK_TREE`, `--work-tree`), and so is a value git expands and the scan does not (`:(optional)`, `%(prefix)`, `~user`, escapes); a quoted value keeps its spaces.
- Also reported: hooks set in config (`[hook "name"] command`), programs a repository's own config names (`core.pager`, `pager.*`, `core.editor`, `sequence.editor`, `core.askPass`, `gpg.program`, `difftool`/`mergetool` commands, a credential helper with a path), and template hooks `clone` and `init` may run (`init.templateDir`, `--template`, `GIT_TEMPLATE_DIR`). The user's own config naming a pager or editor is not reported. git config is read once per folder for the whole command.
- `-n` skips commit's hooks only for commit: an alias set that also defines `co = checkout` no longer keeps them in the list.
- After the user refuses a command as a mismatch, the result tells the agent its two ways forward: change the command so it does only what was asked, or hand it again with a reason that states everything it does, including what the check found missing, so the user can judge it. It is told not to reword the reason only to pass the check, and to ask the user when the command goes against their request. Before, it was only told to ask.
- A test that read the saved check model before its background write finished now waits for it.

## 0.7.1

- git config is read the way git reads it where that is safe, and over-read where it is not, so a setting that runs code cannot hide in an odd layout: CRLF line ends, escaped quotes in section names, old `[section.sub]` headers, entries on the header's line, and the config read both with and without backslash line continuation (only CRLF or LF ends a line; a lone CR does not). Every value of a setting counts, not the last one. Fixes a 0.7.0 case where `[filter "a\"b"]` hid its filter command.
- git aliases are no longer resolved. When the command names an alias (`alias.<name>`, `[alias "<name>"] command`, or `-c alias.<name>=`), any alias in the config that runs a shell (`!`) gets the shell note, and hooks are checked when any alias value names a hook verb, whatever its quotes, escapes, comments, or chain of aliases. `-n` skips commit's hooks only when commit is the one verb the alias may reach. `GIT_CONFIG_*` and `--config-env` give a "git config set at runtime" note. The check stays linear in the config's size.

## 0.7.0

- The selector lists what the checks could not read, found by code and shown whatever a verdict says: **Not readable** (a file the command runs is missing, not a regular file, a project binary, or protected by `secret_drop`), **Not followed** (code from a download piped to a shell, standard input, a process substitution, a runtime path or command name, a glob, a package `npx`/`dlx` may download, install scripts, or a task runner such as `just`), **Read in part** (a file over 16 KB, with its size), and **Not read** (past the five-file or three-level limit). Before, such files were skipped silently, and a check judged from the command's words alone.
- The checks follow what the command runs, by reading files only: the makefile (`-f`, `-C`, includes, continuation lines, recipes after `;` on a rule line, `$(shell …)`, variables set to a literal value) for `make`; the `package.json` script for `npm run`/`npm test`/`pnpm`/`yarn`/`bun run`, with npm's `pre` and `post` scripts, looked up as an own string key so a name such as `constructor` is not a script; a module in the folder for `python -m`; shell scripts the command or a script runs, here-documents and here-strings fed to a shell, `sh -c`/`eval` strings, `find -exec`, and substitutions inside arithmetic, `${…}`, array literals, and unquoted here-documents, three levels deep. A script's relative path is looked up from the command's folder (following literal `cd`, which ends with its subshell or substitution; after `popd` the folder is unknown), then the script's own. Comments, quoted here-documents, `case` patterns, and `[[ … ]]` operators are not taken for commands.
- Also reported as not followed: lifecycle verbs (`npm publish`, `pack`, `version`), more install verbs (`update`, `link`, `ci` aliases), `create`/`npm init <pkg>`, `yarn workspace`, test and build runners (`node --test`, `pytest`, `jest`, `vitest`, `cargo run/test/build`, `go run/test`, `dotnet`, `pip install`), and git commands that run hooks when the repository has hooks or sets `core.hooksPath`.
- Where the scan cannot tell, it lists that instead of guessing. A `cd` that may not run or runs in a child (after `||`, in a pipeline or `&`, inside `if`, a loop, `case`, `{ … }`, or a function), `popd`, and sourcing a file that changes folder or could not be read leave the folder unknown; after an `&&` list holding a `cd` ends, the folder is unknown too (inside the list the `cd` holds); `eval` changes it as the shell does. `function name { … }` bodies count as functions. Command substitutions nested past eight levels, makefiles that use `define`/`$(call)`/`$(eval)`, make variables that resolve to nothing known, sourced credential files that run commands, git aliases that run a shell (`!`), hooks from `-c core.hooksPath`, user or system git config and the files it includes, git config that runs a command (a `!` credential helper or `core.sshCommand` for commands that talk to a remote, `core.fsmonitor`, filter, diff, and merge drivers other than git-lfs), `python -m pytest`/`unittest`/`pip install`, `bun test` without a `test` script, and hooks `--no-verify` does not skip are listed too. `((cmd) )` is two subshells, not arithmetic; a quoted `case` is a command; ANSI-C strings (`$'\x2e'`) are decoded. Files loaded before a program (`--require=./x.js`, `--import`, `ruby -r`, `php -d auto_prepend_file`, `BASH_ENV`, `ENV`, `NODE_OPTIONS`, also when exported) are read.
- Both checks get the list (`unread` for Jev, a fenced JSON list for `e`), and a match from either becomes partial while the list is not empty (`capped`), so text in a script cannot argue the checker into a match. The agent's result names what was not read and `details.unread` counts it.
- Secrets: files whose names commonly hold credentials (`.env` files, `.envrc`, `.netrc`, `.npmrc`, shell startup files such as `.bashrc` and `.zshrc`, `kubeconfig`, service-account JSON, keys and certificates, `*.ini`, `*.conf`, `*.properties`, `*.tfvars`, and any name with `secret`, `credentials`, `password`, `token`, or `api_key` as a word, whatever its extension) are never sent, even when the command sources or includes them; they are listed as not readable. `--env-file` and php's `-c` take a value instead of naming the script. Script text is redacted, then cut to 16,000 bytes (not characters), so the cut cannot land inside a secret the read holds whole; a package script's name and a script's path are redacted too. Everything the scan sends also has literal values of credential-like names (`API_KEY=…`, `"password": "…"`, judged by the name's words, so `AUTHOR` is not one), credential options (`--password`, `--token`, `curl -u user:…`, `sshpass -p`), `Authorization: Bearer …`, known token formats (`sk-…`, `sk_live_…`, `ghp_…`, `npm_…`, `AKIA…`, JWTs, private keys), and passwords in URLs, even with an empty user, replaced by `[REDACTED]`; a value built at runtime (`$(…)`) and a path are kept, the scan parses the text as read, so masking hides no command from the scan, and a masked value that may be code is listed. The masking runs in time linear in the text.
- Injection: script names reach the `e` checker as JSON strings, so a file name with a newline cannot start its own instructions. Only regular files are opened (FIFOs and devices are checked first and never opened, so a waiting writer is not released and a serial device is not reset); the open is non-blocking and the handle is checked again, so a file swapped for one cannot stall the selector. A plain argument costs a two-byte read, not a full one. The selector, the tool call, and the checker's words show controls, format characters (bidirectional marks, zero-width and tag characters, soft hyphens), variation selectors, spaces other than the ASCII one, blank fillers, and runs of three or more combining marks as `\u{…}` escapes instead of drawing them.

## 0.6.1

- The `e` check no longer calls a command a mismatch because it serves only one step of the user's request, or because the request is about something else (in a live test, the user was testing the check itself and a model judged a harmless command against that). "Goes against the user's request" now means works against it: does what the user forbade, undoes what they asked for, or takes another way than the one they chose; the distance from the request goes in `gaps`. The Jev check is unchanged.

## 0.6.0

- `robot_hand`: when pi has TypeSafe's Jev classifier (`typesafe/jev-latest`, in a pi with classifier models) and TypeSafe has a credential, Jev checks the command as the terminal selector opens. It reads the same redacted input as the `e` check (command, scripts, reason, the user's last message and later dialog answers, the untrusted log) and returns `match`, `partial`, or `mismatch` with probabilities, shown above the choices. `"jevCheck": false` in `~/.pi/agent/robot-hand.json` turns it off; it is on by default. A failure shows only the HTTP status, never the provider's text. Closing the selector aborts it. The verdict goes into the tool result and `details.jev`.
- When the Jev check or the `e` check says `mismatch`, the selector adds "Report the mismatch and refuse". It works like "No, thanks" (places and runs nothing, leaves the agent's turn open) and also tells the agent the reason: `details.status: "refuse"`, and the result says a check found a mismatch, with each verdict. The published dialog settles as a cancel; its labels and digest are unchanged.

## 0.5.5

- The `e` check also redacts secrets the user gave `secret_drop` with `format: "command"`. Those reach no file, so no registry records them; `secret_drop` now answers `secret-drop:redact` requests on pi's event bus with its in-session redactor, and the check runs every text through it as well as through the registry. The value never travels on the bus; when several extensions answer, each redacts what the earlier ones returned.
- `/secret-drop forget` no longer drops values fed to a command from redaction for the rest of the session; before, any `forget` unmasked them in the main model's context too.

## 0.5.4

- A reply typed into `secret_drop` goes to the checker as the sentence the user typed, not as the tool's whole record; its other statuses are left out. In a live test the record's agent-written command and target buried the reply, and the checker judged a command that followed it a mismatch.
- The checker is told that a later answer that changes how the user wants something done replaces the earlier way, and that handing a command over keeps a request that the agent run nothing itself.

## 0.5.3

- The `e` check counts answers given in dialog tools as the user's, not only `secret_drop` replies: `ask_user_question` and `ask_user` are built in, and `dialogTools` (a list of tool names) in `~/.pi/agent/robot-hand.json` adds more. A dialog tool's details go to the checker whole, without parsing its format; each string field is redacted first and cut to 300 characters (start and end), the record to 1,500, and all answers to the latest 6,000. The checker is told that only what the user typed or picked is theirs; questions, option labels, previews, commands, and reports were written by the agent or the tool. Other tools' details stay out.

## 0.5.2

- The check's model list puts the provider pi is using now first. pi lists every model of a provider that has a stored credential, even an expired one, so a provider whose check failed is marked `(sign-in failed)` or `(check failed)` and moved to the end for the rest of the session; a successful check clears the mark. The filter line reads `Filter:`.

## 0.5.1

- The `e` check reads a reply the user typed into `secret_drop`'s dialog from the tool's details, not its text, and lists it as the user's; the rest of what happened after the user's last message goes to the checker fenced and marked untrusted, and cannot change the user's request. Before, tool output could imitate a user reply and turn a mismatch into a match.
- Secret values are redacted before any text is cut (the user's message, the log, replies, scripts), so a secret that straddled a cut no longer reaches the checker in part.

## 0.5.0

- `robot_hand`: press `e` in the terminal selector to have another model check the command. It reads the command, the scripts the command runs (files with a script extension or a `#!` line, up to five, 16 KB each; files `secret_drop` protects and its staging folder are never read), the agent's reason, the user's last message, and what happened after it (agent text and tool results, up to 2,000 characters, so a reply given inside `secret_drop` or a question dialog counts), and shows what the command will do and whether that matches: match, partial, mismatch, or unclear. The first `e`, and the next one after a failed check, asks which signed-in model to use; `E` always asks. The choice is saved as `checkModel` in `~/.pi/agent/robot-hand.json`. Known `secret_drop` values in the command, scripts, reason, and message are replaced with `[REDACTED]` before sending; an unreadable or unknown secret_drop registry fails the check and sends nothing. Command and script text go to the checker fenced, marked as data. The checker answers in the language of the user's last message, or of the reason when there is none. Starting a new check aborts the one still running. The check never blocks a choice; when the user checked, the tool result carries the verdict and `details.check`. In the terminal UI the selector is now robot_hand's own component (↑↓ or j/k, stopping at the ends as before); `app.tools.expand` does not work while it is open. RPC clients keep pi's selector and get no check. The dialog contract (title, labels, digest) is unchanged.
- `secret_drop`: Tab now opens a reply instead of a question. The user can ask a question or leave a note such as where the secret already is. The result tells the agent to answer a question and call again, or to use the stated location without reading the value and not ask again. A location the user names in a note is not guarded like a destination `secret_drop` wrote; the result and docs say so. `details.status` is `"reply"` (was `"question"`).

## 0.4.0

- The two Herdr pane choices now carry `next: "pane"` and `tagged: true` in `robot-hand:pending`, and "Put it in my prompt" carries `next: "terminal"` (hints, not hashed). When another extension's answer picks a pane choice, the new pane is marked with `herdr pane report-metadata <pane_id> --source robot-hand --token sb_answer=<answerId> --ttl-ms 600000` right after the split and before the command is typed or run, so Straw Boss grants its terminal keys to that pane and no other. Tagging is tried once; a failure does not stop the command. A pick in the terminal tags nothing.

## 0.3.2

- Tighter browser preparation for `secret_drop`: only pages that newly create a secret are prepared, and only in a browser session already open on the user's signed-in profile. After preparing, the agent makes no browser call in that session until the user says the tab is closed, whatever `secret_drop` returns, because browser tools return page content. Pages that show an existing secret are never opened by the agent, since the value is already in their DOM. A token created on a prepared page and not applied is revoked.

## 0.3.1

- `secret_drop` guidance: when a secret is created or revealed on a web page and the agent can drive the user's signed-in browser, the agent first asks whether to prepare that page up to its final create or reveal button, so the user only presses it and copies the value. The agent leaves that tab unread until the value is applied.

## 0.3.0

- `robot_hand` becomes a dialog owner of dialog contract v1: it publishes `robot-hand:pending` for the selector it opens and accepts one validated `robot-hand:answer` from another extension, replying with `robot-hand:answer-result` and `robot-hand:closed`. See "Answering from another extension" in the README.
- A remotely answered call returns the same result text as a terminal pick; `details.answeredFrom` is `"browser"`.
- Terminal behavior is unchanged. `secret_drop` publishes nothing.
